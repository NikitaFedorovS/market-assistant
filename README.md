# market-assistant — AI-ассистент маркетплейса с фирменной персоной

Ассистент поддержки маркетплейса на open-source LLM. Модель дообучается через **LoRA/QLoRA** под
персону бренда, отвечает по базе знаний через **гибридный RAG**, сама выполняет действия через
**tool calling** и обслуживается **vLLM** на собственном GPU. Дешёвый **роутер на ruBERT-tiny2**
отсекает простые запросы до LLM. Отдельный **сервис на SDXL/Flux** генерирует фоны для фото товаров.

Цикл целиком: **синтетические данные → чистка → QLoRA → оценка «до/после» → RAG + агент →
vLLM + мониторинг → нагрузочный тест**.

> Это пет-проект. Реальных логов поддержки нет, поэтому «бизнес» синтетический: каталог на 5 000
> товаров, 3 000 заказов в SQLite, база знаний на 72 статьи (ru/uz) и сгенерированные диалоги.
> Пайплайн устроен так же, как для настоящих логов: PII-маскирование, фильтры шума и
> стилизация через teacher-LLM включаются конфигом.

## Архитектура

```
Сообщение (ru / uz / смешанное)
   │
   ▼
[1] Роутер — правило «позовите оператора» → ruBERT-tiny2 (CPU, ~1–2 мс)
   │   order_status · return · product_question · faq · chitchat · human_handoff
   │      ├─ human_handoff ─────► оператор (без LLM)
   │      └─ chitchat ──────────► LLM без tools (короткий путь)
   ▼
[2] RAG (для faq / return) — BM25 + BGE-M3 (Qdrant) → RRF → (опц. ре-ранкер) → бюджет токенов
   ▼
[3] Агент — Qwen2.5-7B-Instruct + LoRA «Dilkash»
   │   tools: get_order_status · create_return · search_products   (Pydantic → JSON Schema)
   │   guard: create_return только после явного «да» · ≤3 шагов · ошибка → оператор
   ▼
[4] vLLM (OpenAI API) — AWQ-база + multi-LoRA · prefix caching · hermes tool parser
   ▼
[5] FastAPI-шлюз — /chat (JSON или SSE) · /health · /metrics → Prometheus → Grafana

[6] Сервис картинок — rembg → SDXL/Flux (diffusers или ComfyUI API) → композит с тенью
```

| Модуль | Что делает |
|---|---|
| `data/policies.py` | единый источник правил: срок возврата, регионы, категории (возвратные или нет) |
| `data/catalog.py` | товары ru/uz, БД заказов, база знаний + вопросы для оценки RAG |
| `data/dialogs.py` | диалоги 6 интентов на ru/uz/смешанном; tool results берутся из **реальных** tools; намеренный шум |
| `data/build_sft.py` | стилизация → PII → фильтры → MinHash-дедуп → system prompt (+ контекст) → микс общих задач → сплиты |
| `train/chat_format.py` | токенизация по chat template Qwen с **маской только на ответах ассистента** |
| `train/train_lora.py` | QLoRA через Unsloth (CUDA) или transformers + PEFT + TRL `SFTTrainer` |
| `train/train_router.py` | дообучение ruBERT-tiny2 |
| `rag/` | чанкинг, Qdrant (embedded / server / in-memory), BM25, RRF, ре-ранкер, бюджет токенов |
| `agent/` | инструменты над SQLite, цикл агента с предохранителями |
| `llm/client.py` | vLLM (OpenAI API) · локальный transformers · scripted (тесты) |
| `eval/` | RAG, роутер, регрессия навыков и tool calling, персона (эвристика + LLM-судья) |
| `app/main.py`, `app/images_main.py` | HTTP-шлюз и сервис картинок |
| `scripts/run_vllm.sh`, `scripts/load_test.py` | запуск vLLM с флагами из конфига; нагрузочный тест на Locust |

## Ключевые решения

| Решение | Почему |
|---|---|
| **Qwen2.5-7B-Instruct** | сильная мультиязычность (включая узбекский), нативный tool calling, Apache-2.0, влезает в одну GPU |
| **QLoRA для обучения** | 7B на одной карте 24 ГБ; адаптер — десятки МБ |
| **LoRA для персоны, RAG для фактов** | персона — это поведение, её можно «зашить» в веса. Сроки, цены и правила меняются, поэтому их берём из базы знаний и инструментов |
| **Маска лосса только на ответах** | модель не учится воспроизводить system prompt, вопросы пользователя и JSON из инструментов |
| **20–25% общих задач в миксе + регрессионный набор** | защита от catastrophic forgetting с измеримой проверкой |
| **Гибрид BM25 + dense** | BM25 ловит точные названия регионов и артикулы, dense — перефразы и смешанный язык |
| **Детерминированный guard на возврат** | необратимое действие не зависит от того, «послушается» ли модель |
| **vLLM + AWQ + multi-LoRA** | continuous batching, одна база в памяти, несколько персон-адаптеров на лету |

## Данные

```bash
make data          # = make synth + build_sft
```

**Синтетика** (`data.synth`): 5 000 товаров, 3 000 заказов, 72 статьи базы знаний (14 регионов
доставки, правила возврата по 12 категориям, оплата, рассрочка, отмена, гарантия и т. д., на ru и uz),
по 1 500 диалогов на интент. Результаты инструментов в диалогах получены вызовом настоящих
`MarketTools` по той же БД, поэтому обучение и прод видят одинаковый формат.

**Шум внесён намеренно**, чтобы фильтрам было что ловить. Фактический прогон:

| Шаг | Сколько |
|---|---:|
| Всего диалогов | 9 277 |
| Маскирование PII (телефоны, карты, e-mail) | 483 замены |
| Отброшено: токсичность | 201 |
| Отброшено: «пустые» ответы («Ок.») | 207 |
| Отброшено: битый JSON / схема tool call | 59 |
| Отброшено: противоречие правилам (срок возврата ≠ 10 дней) | 62 |
| Отброшено: near-duplicate (MinHash, порог 0.9) | 4 827 |
| **Осталось доменных диалогов** | **3 921** |
| + общие задачи (арифметика, логика, JSON, сортировка) | 1 307 (25%) |
| Сплит train / val / test | 4 706 / 261 / 261 |

Каждый фильтр поймал ровно столько шума, сколько было внесено. **Near-dup выкинул половину
корпуса**: шаблонная синтетика однообразна, особенно для chitchat и handoff. Это честное
ограничение. Для разнообразия есть режим teacher-LLM (`sft.teacher_base_url`): сильная модель
переписывает ответы оператора по гайду [`configs/persona.md`](configs/persona.md).

## Результаты

> Обучение 7B требует CUDA GPU. Ниже фактические прогоны на Apple M3 Pro: роутер и RAG — на
> полных данных, персона — на **Qwen2.5-0.5B** как проверка пайплайна (300 шагов). На 7B цифры
> персоны и регрессии нужно перемерить; команды те же.

### Роутер (ruBERT-tiny2, 3 эпохи, ~1 мин на M3 Pro)

| | значение |
|---|---:|
| macro-F1 (test, 797 фраз) | **0.933** |
| F1: order_status / return / product_question / faq | 0.998 / 1.000 / 1.000 / 1.000 |
| F1: chitchat / human_handoff | 0.741 / 0.857 |
| задержка на CPU, p50 / p95 | 1.1 мс / 1.6 мс |

Слабые классы — chitchat и handoff: для них меньше всего уникальных шаблонов (после дедупа
осталось 48 и 37 диалогов). На сквозном прогоне «позовите оператора» модель угадала, но с
уверенностью 0.37 < порога 0.6, и запрос ушёл в faq. **Вывод:** явная просьба позвать оператора
теперь ловится правилом *до* модели (`wants_operator`), потому что пропущенный handoff — самая
дорогая ошибка. Модель остаётся для всего остального.

### RAG (178 вопросов к 72 статьям, уровень документа)

| setup | Recall@1 | Recall@5 | MRR | мс/запрос (CPU) |
|---|---:|---:|---:|---:|
| BM25 | 0.961 | 0.972 | 0.967 | 0.04 |
| dense: rubert-tiny2 | 0.669 | 0.893 | 0.754 | 1.8 |
| hybrid: BM25 + rubert-tiny2 | 0.865 | 0.978 | 0.914 | 1.9 |
| dense: multilingual-e5-small | 0.972 | 0.989 | 0.980 | 9.6 |
| hybrid: BM25 + e5-small | **0.983** | 0.989 | **0.987** | 9.6 |
| dense: BGE-M3 | 0.938 | 0.994 | 0.964 | 76 |
| **hybrid: BM25 + BGE-M3** | **0.983** | **0.994** | **0.987** | 76 |
| hybrid + bge-reranker-v2-m3 | 0.888 | 1.000 | 0.940 | 7 206 |

- Гибрид лучше каждого компонента по отдельности: RRF чинит промахи dense на точных названиях регионов.
- rubert-tiny2 как эмбеддер слаб (он хорош как классификатор, но не для поиска), особенно на узбекском.
- **Ре-ранкер ухудшил Recall@1 (0.983 → 0.888)** и добавил 7 с на запрос на CPU. Разбор промахов
  на подвыборке: ре-ранкер ставит наверх ту же статью на другом языке (ru ↔ uz «близнецы»).
  Поэтому в конфиге он **выключен по умолчанию**. Следующий шаг — фильтр кандидатов по языку
  запроса перед ре-ранкингом.
- e5-small почти догоняет BGE-M3 при 8× меньшей задержке на CPU. На GPU разница несущественна,
  в проде оставлен BGE-M3 (лучше Recall@5 и мультиязычность).

### Персона-LoRA: Qwen2.5-0.5B, 150 шагов (~27 мин на MPS), база vs LoRA

Обучение: loss 1.32 → 0.14, eval_loss 0.047. Низкий loss в основном говорит о том, что синтетика
шаблонная, а не о качестве. Поэтому главное — оценки ниже. Обеим моделям дан одинаковый system
prompt персоны, то есть LoRA сравнивается с хорошим промптингом, а не с «голой» моделью.

**Регрессия навыков и tool calling** (held-out задачи, greedy decoding):

| группа | база | LoRA |
|---|---:|---:|
| tool calling (правильный инструмент и аргументы) | 0.500 | **1.000** |
| текстовые задачи | 0.667 | 1.000 |
| арифметика | 0.733 | 0.733 |
| JSON-извлечение | 1.000 | 1.000 |
| инструкции («одним словом») | 0.200 | 0.200 |
| **сортировка чисел** | 0.267 | **0.067** ⚠️ |
| итого | 0.536 | 0.691 |

**Итоговый скор вырос, но сортировка просела.** Сначала проверка регрессии смотрела только на
итог и такую просадку пропустила бы. Теперь она ещё и падает, если любая группа просела больше
чем на 10 п.п. (`results/regression_gate.json`: `sorting 0.267 → 0.067`). Разбор: обе модели
сортируют числа как строки (`17, 171, 18`), LoRA к тому же исказила одно число. В обучающем миксе
сортировка шла только на числах 1–99, а в регрессии — до 200: разрыв распределений. Исправление —
разнообразнее общий микс; на 7B проблема, скорее всего, слабее, но гейт должен это подтвердить.

**Персона** (80 held-out диалогов, эвристические метрики — прокси, см. ограничения):

| метрика | база | LoRA |
|---|---:|---:|
| узбекские словечки в русских ответах | 0.350 | **0.900** |
| обращение на «ты» | 0.775 | **1.000** |
| нет выдуманных чисел (относительно эталона) | 0.637 | **0.812** |
| ≤ 1 эмодзи / краткость (1–4 предложения) | 1.000 / 0.825 | 0.975 / 0.850 |
| **style score** | 0.718 | **0.907** |

### Сквозной прогон API (0.5B + LoRA через transformers-бэкенд)

| запрос | что произошло |
|---|---|
| «где мой заказ 100035?» | роутер → `get_order_status` → «Hop, Заказ 100035 в пути, ожидаем 22 октября.» ✅ |
| «хочу вернуть заказ 100007, не подошёл размер» → «да» | вопрос-подтверждение → `create_return` → «Готово ✅ Возврат … оформлен» ✅ |
| «Сколько идёт доставка в Самарканд?» | RAG → нужная статья → точный ответ ✅ |
| «Как оформить рассрочку?» (SSE) | route → retrieve → reply, ответ по статье ✅ |
| «позовите оператора» | правило → handoff без вызова LLM ✅ |
| «Qanday to'lov usullari bor?» | RAG нашёл верную статью первой, но 0.5B смешала её с соседними ❌ |
| «есть наушники JBL до 1 000 000 сум?» | инструмент вернул 5 товаров, 0.5B сформулировала ответ с мусором ❌ |

Ошибки последних двух строк — предел модели на 0.5B: инструменты и поиск отработали верно.
Именно для этого целевая модель — 7B.

> LoRA обучена до исправления генератора дат заказов (у заказов «в пути» ETA могла быть в прошлом).
> Исправление затрагивает только даты в результатах инструментов, а не стиль или вызовы
> инструментов. Данные, роутер и RAG выше пересчитаны на исправленной версии.

## Запуск

### Локально (Mac / CPU): данные, роутер, RAG, тесты, API с маленькой моделью

```bash
make install
make data
make train-router
make index
make eval                       # RAG + роутер → results/
make test && make lint

# пробная LoRA на 0.5B (MPS/CPU)
MA__TRAIN_LORA__BASE_MODEL=Qwen/Qwen2.5-0.5B-Instruct MA__TRAIN_LORA__LOAD_IN_4BIT=false \
MA__TRAIN_LORA__OUTPUT_DIR=models/persona-lora-0.5b MA__TRAIN_LORA__PAD_TO_MULTIPLE_OF=256 \
MA__TRAIN_LORA__BATCH_SIZE=2 MA__TRAIN_LORA__MAX_SEQ_LEN=1536 \
make train ARGS="--max-steps 300 --max-eval-samples 120"

# API на локальной модели вместо vLLM
MA__SERVE__LLM__BACKEND=transformers MA__SERVE__LLM__LOCAL_ADAPTER=models/persona-lora-0.5b make serve-local
```

### GPU-сервер: QLoRA 7B + vLLM + мониторинг

```bash
make install-gpu                  # + unsloth
make data && make train           # Qwen2.5-7B, QLoRA NF4, ~1–2 ч на RTX 4090 / L4
make train-router
MA__RAG__QDRANT_URL=http://localhost:6333 make index   # после `docker compose up -d qdrant`
make serve                        # vllm + api + qdrant + prometheus + grafana
make eval-llm ARGS="--backend openai --base-model-name Qwen/Qwen2.5-7B-Instruct-AWQ"
make load-test
make images                       # сервис картинок (профиль compose `images`)
```

> Для сервинга vLLM берёт квантованную AWQ-базу, а адаптер обучен на базе в bf16. Это стандартная
> практика, но качество пары «AWQ + адаптер» нужно проверить отдельно: `make eval-llm` против vLLM.

Grafana: `http://localhost:3000` (дашборд «Market assistant»: KV-cache, running/waiting, TTFT p50/p95,
tokens/s, задержка шлюза, доля handoff, ошибки tools).

### Флаги vLLM и защита от OOM

`scripts/run_vllm.sh` читает значения из `configs/serve.yaml` (любое можно переопределить через env):

```
--model Qwen/Qwen2.5-7B-Instruct-AWQ --quantization awq
--enable-lora --lora-modules persona=models/persona-lora --max-loras 4 --max-lora-rank 16
--max-model-len 8192 --gpu-memory-utilization 0.85 --max-num-seqs 64
--enable-prefix-caching --enable-auto-tool-choice --tool-call-parser hermes
```

Чек-лист против OOM:
- `max-model-len` ограничивает KV-cache на последовательность;
- `gpu-memory-utilization` оставляет запас под CUDA graphs и сервис картинок;
- `max-num-seqs` подбирается нагрузочным тестом;
- жёсткий бюджет RAG-контекста (`rag.context_token_budget`);
- AWQ-база;
- пайплайн картинок с `cpu_offload`, выгружается из VRAM после простоя (`images.unload_after_s`).

## API

```bash
curl -s localhost:8000/chat -H 'Content-Type: application/json' \
  -d '{"message": "где мой заказ 100007?"}'
# {"session_id": "...", "reply": "Сейчас гляну 👀 Заказ 100007 ...", "intent": "order_status",
#  "handoff": false, "events": [{"type": "route", ...}, {"type": "tool", "name": "get_order_status", ...}]}

curl -sN 'localhost:8000/chat?stream=true' -H 'Content-Type: application/json' \
  -d '{"message": "Qanday to'"'"'lov usullari bor?"}'       # SSE: route → retrieve → message → reply → done

curl -s localhost:8002/images/background -F image=@product.jpg -F style=kitchen -o out.png
```

SSE отдаёт события агента (маршрут, вызовы инструментов, ответ), а не стриминг токенов.
Пошаговый стриминг токенов финального ответа — один из следующих шагов.

## Тесты

```bash
make test    # 66 тестов: данные/PII/фильтры, tools, агент (scripted LLM), RAG (fake embedder), роутер, API, картинки
make lint    # ruff + black
```

Тесты не скачивают модели: LLM — scripted-клиент, эмбеддер — детерминированный хеш,
Qdrant — in-memory, БД — мини-генератор во временной папке.

## Ограничения и развитие

- **Синтетика ≠ реальные логи.** Мало лексического разнообразия (это видно по дедупу и роутеру),
  тест-сеты из того же распределения. Нужны реальные анонимизированные чаты или teacher-LLM.
- **Метрики персоны на 0.5B** — только проверка пайплайна; эвристическая оценка стиля — прокси,
  LLM-судья смещён, его нужно подкреплять слепой ручной разметкой.
- **RAG-вопросы шаблонные** и часто содержат ключевые слова статьи, поэтому BM25 выглядит сильно.
  На живых запросах разрыв в пользу dense/гибрида обычно больше.
- **Сессии в памяти процесса**: для нескольких реплик шлюза нужен Redis.
- Дальше: DPO на парах «хороший/плохой ответ», guardrails (модерация входа и выхода), стриминг
  токенов, спекулятивный декодинг в vLLM, A/B на реальном трафике.
